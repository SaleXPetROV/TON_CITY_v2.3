# Внутриигровые задания и новый онбординг — описание изменений

## Коротко
1. **Задания внутри игры:** «Путь новичка» (7 шагов), 3 цели на день, 3 цели на неделю. Прогресс считается сам по реальным действиям игрока; нажатие на плашку ведёт на нужный экран; по готовности — кнопка «Забрать».
2. **Обучение по A/B:** половина новых игроков вместо принудительного тура из 15 шагов получает «Путь новичка». Старые игроки не затронуты. Финальная награда (ресурс тира 3) переехала в конец «Пути новичка» и не выдаётся дважды.
3. **Подсказка на простаивающем бизнесе:** «Для работы не хватает: X — Купить» с переходом в торговлю, уже отфильтрованную по ресурсу.
4. **Ежедневная награда:** кроме старого условия «купить 30 и продать 95» её открывает любая одна выполненная цель дня.
5. **Исправлены две ошибки** в старом коде (поиск пользователя по пустому кошельку).
6. **Переводы через LibreTranslate на все 9 языков** (en, ru, es, zh, fr, de, ja, ko, **id**): тексты заданий переводятся и сохраняются в базе, а для всего интерфейса есть скрипт, который находит недостающие переводы, переводит и сохраняет их в файл (см. раздел «Переводы»).

---

## Как игрок выполняет задания
- Внутриигровые задания: **кнопки «Выполнить» нет**. Игрок нажимает на плашку → попадает на нужный экран → делает действие как обычно → прогресс растёт сам → появляется «Забрать».
- Внешние задания (подписка, ссылка, TikTok, репост) работают как раньше: «Открыть → Проверить».

## Награды
- $CITY за задания идут на **бонусный баланс** (`bonus_balance`): тратится в игре, не выводится. Это защищает от фарма мультиаккаунтами.
- XP идёт в `users.xp`.
- Дневной лимит бонусов с заданий: **300 $CITY** (меняется в админке через API, см. ниже).
- Финал «Пути новичка»: игрок сам выбирает 1 ресурс тира 3 (как в старом обучении, хранится как `<ресурс>_tutorial`, не продаётся).

| Задание | Что засчитывает | Награда |
|---|---|---|
| ob_open_business | есть хотя бы один бизнес | 20 $CITY + 10 XP |
| ob_first_shift | запуск смены | 10 + 30 XP |
| ob_first_collect | сбор продукции | 10 + 30 XP |
| ob_first_buy | покупка на рынке | 15 + 20 XP |
| ob_first_sale | продажа другому игроку | 25 + 30 XP |
| ob_first_repair | ремонт | 10 + 20 XP |
| ob_first_upgrade | улучшение (включая 0 → 1) | 100 + 100 XP |
| Ежедневные (по одной каждой сложности) | смена, сбор / продать 20, купить 20, ремонт / лот, продать 50 | 5 / 10 / 15 $CITY + XP |
| Недельные | продать 300; 3 ремонта или улучшения; 7 смен | 60 / 40 / 50 $CITY + XP |

Суммы стартовые, их стоит проверить на балансе экономики. Все шаблоны хранятся в коллекции `quest_templates` и меняются через админский API без деплоя.

## Изменённые и новые файлы

### Бэкенд
**Новый `backend/quests.py`** — весь движок:
- шаблоны заданий (засеваются в `quest_templates` при первом запуске, правки админа не затираются);
- `fire(user, event, amount, unique)` — сообщить о действии игрока (не блокирует запрос и никогда не ломает игровое действие при ошибке);
- `fire_sale(seller, buyer, amount)` — продажа; **не засчитывается**, если у продавца и покупателя общее устройство по данным антифрода (`fingerprints.visitor_id`);
- выдача ежедневных и недельных целей под игрока (стабильно в течение дня/недели, только тем, у кого есть бизнес);
- атомарное получение награды (двойное нажатие не платит дважды), дневной лимит, запись в `transactions` (`tx_type: quest_reward`);
- режим онбординга и группы A/B, финальная награда, статистика;
- простая аналитика в коллекции `analytics_events` (группа онбординга, полученные награды, завершение пути) — без паролей, токенов и кошельков.

Новые коллекции: `quest_templates`, `user_quests`, `quest_assignments`, `quest_event_log`, `analytics_events`. Поля пользователя: `onboarding_group`, `onboarding_group_at`, `onboarding_completed_at`, `quest_bonus_today`.

**`backend/server.py`:**
- импорт и подключение роутера заданий;

**`backend/routes/repair.py`, `routes/business_mgmt.py`** — события «ремонт», «улучшение» (оба пути, включая 0 → 1), «сбор дохода».

**`backend/routes/tasks.py`** — ежедневная награда открывается старым условием **или** любой выполненной целью дня; в ответ `/api/tasks/daily` добавлено поле `quest_goal_done`.

**`backend/routes/tutorial.py`** — `/api/tutorial/status` назначает игроку группу онбординга и для группы «quests» отвечает `completed: true`, поэтому тур не стартует. Добавлены поля `onboarding_mode` и `onboarding_group`. Всё остальное в обучении не тронуто.

**Новый `backend/tests/test_quests.py`** — 13 тестов на изолированной in-memory базе (прогресс, повторное получение, одновременные запросы, уникальные события, выдача целей, лимит, связанные аккаунты, группы и финальная награда, ежедневная награда; перевод и сохранение текстов, отказ сохранять испорченный перевод, приоритет ручного текста, работа без LibreTranslate).

## Переводы (LibreTranslate, 9 языков)
В проекте 9 языков: en, ru, es, zh, fr, de, ja, ko, id. Вручную пишутся только **английский и русский**, остальные 7 переводятся через ваш LibreTranslate (`LIBRETRANSLATE_URL`, по `libretranslate.supervisor.conf` это `http://127.0.0.1:5000`). Запасной вариант через LLM для этих переводов не используется.

### Тексты заданий (бэкенд)
- Переводятся с английского и **сохраняются прямо в шаблоне задания** в MongoDB: `quest_templates.title.<язык>`, `quest_templates.description.<язык>`. Машинный перевод помечается `i18n_auto.<поле>.<язык> = true`.
- **Когда:** при старте сервера в фоне переводятся все задания на все языки; если игрок открыл задания на языке, которого ещё нет, сервер ждёт перевод до 5 секунд (дальше доводит в фоне, а игрок один раз видит английский). Готовые переводы больше не запрашиваются.
- **Защита переменных:** `{amount}`, `{{x}}`, `%s`, `$CITY`, `TON`, `GRAM City`, ссылки и переносы строк не отдаются переводчику. Если сервер потерял что-то из этого, перевод не сохраняется и будет повторён позже.
- **Ручной текст главнее:** если админ вписал перевод сам, машинный его не перезапишет. Если админ меняет английский текст, машинные переводы удаляются и делаются заново.
- Сообщения об ошибках заданий для игрока: en/ru вручную, остальные языки через LibreTranslate с кешем в `translation_cache`.
- Новая функция `translation_service.translate_libre_protected()` — перевод только через LibreTranslate с защитой переменных.

Админский API:
| Метод | Путь | Назначение |
|---|---|---|
| PUT | `/api/admin/quests/templates/{id}` | теперь принимает и тексты: `{"title": {"en": "...", "id": "..."}, "description": {...}}` |
| POST | `/api/admin/quests/translate?lang=id&force=false` | перевести сейчас (все языки или один; `force` переделывает только машинные) |

### Интерфейс (фронтенд)
Проверка показала **2772 отсутствующих перевода** в общих словарях интерфейса: индонезийский — 137 строк, испанский — 359, китайский — 373, французский — 474, немецкий — 476, японский — 477, корейский — 476. Сейчас на месте этих строк показывается английский.

Для этого добавлен скрипт `frontend/scripts/i18n-autofill.cjs`:
```
cd frontend
npm run i18n:check                                        # посчитать пропуски
LIBRETRANSLATE_URL=http://127.0.0.1:5000 npm run i18n:autofill
npm run i18n:autofill -- --langs=id                       # только индонезийский
```
- Охватывает словари: `translations`, `pageTranslations`, `translationsExtra`, `resourceI18n`, `businessI18n`, `buffI18n`, `contractI18n`, `BUSINESS_NAMES`, `RESOURCE_NAMES`, `TUTORIAL_UI`, `TUTORIAL_STEP_TEXTS`. Учитывает порядок поиска в `useTranslation` (ключ, переведённый в одном из трёх словарей, не считается пропуском и не перекрывается).
- **Где сохраняется:** `frontend/i18n/auto-translations.cache.json` (все переводы с исходником; при повторном запуске переводится только новое или изменённое), `frontend/src/lib/translationsAuto.json` (то, что загружает приложение), `frontend/i18n/auto-translations.report.json` (отчёт и строки, которые не удалось перевести). Файлы стоит коммитить.
- `frontend/src/lib/i18nAuto.js` подключён первой строкой в `src/index.js` и подставляет переводы **только в пустые места** — ручные переводы никогда не перезаписываются.
- В `src/lib/resourceConfig.js` добавлен `export` для `RESOURCE_NAMES` (нужен скрипту и подстановке).

**Важно:** сами переводы интерфейса в архиве ещё не сгенерированы (`translationsAuto.json` пустой). Модели LibreTranslate скачиваются с `argos-net.com`, а этот домен в моей среде был закрыт. Скрипт и подстановку я проверил на тестовом сервере с тем же API. Запустите `npm run i18n:autofill` на сервере, где работает ваш LibreTranslate, и закоммитьте получившиеся файлы.

**Не охвачено скриптом:** небольшие словари, объявленные прямо внутри компонентов (например, подписи в `QuestBoard.jsx`, `TasksPage.jsx`). Подписи, которые добавил я, уже написаны на всех 9 языках вручную.

## Настройка
В `backend/.env`:
```
# tutorial — старый тур для всех; quests — задания для всех новых; ab — 50/50 (по умолчанию)
ONBOARDING_MODE=ab
# ваш сервер LibreTranslate (без него задания показываются на en/ru, остальные языки — английский)
LIBRETRANSLATE_URL=http://127.0.0.1:5000
# LIBRETRANSLATE_API_KEY=...   # если сервер требует ключ
```
Группа закрепляется за игроком один раз и не меняется при смене режима. Игроки, которые уже начинали или проходили обучение, получают группу `legacy` и ведут себя как раньше.

Как принять решение по A/B: через 1–2 недели откройте `/api/admin/quests/onboarding-stats` и сравните группы `quests` и `tutorial`. Если `quests` не хуже, поставьте `ONBOARDING_MODE=quests`, а затем отдельной задачей удалите песочницу обучения.

## Известные ограничения и что дальше
1. **Качество машинного перевода** зависит от моделей LibreTranslate. Посмотрите индонезийский и азиатские языки глазами носителя; плохие строки исправьте вручную — они больше не будут перезаписаны.
2. Подсветки нужной кнопки после перехода по заданию и всплывающего «+1 к заданию» на других экранах пока нет.
3. Продажи по старому эндпоинту `/trade/resource` (встречные ордера) в задания не засчитываются: там продавец определяется не сразу.
4. **Нужно исправить отдельно:** ещё около 45 мест в `server.py` ищут пользователя по `{"wallet_address": current_user.wallet_address}` без проверки на пустое значение (аренда склада, покупка участка с перепродажи, постройка, снос и др.). Защита в `core/balance.py` не даёт списать деньги с чужого игрока, но у игроков без кошелька эти действия теперь будут отвечать «недостаточно средств», пока места не переписаны.
5. Достижения, лиги, цели острова, умные уведомления в Telegram — следующие этапы плана удержания.

# Ускорение админки: одобрение вывода и выкуп ресурсов

## Причина
После одобрения вывода, отклонения, выкупа лотов и удаления лота сервер **ждал доставки уведомления пользователю внутри запроса админа**:
- отправка в Telegram — до 2 попыток по 10 секунд, а если бот не ответил, ещё и запасной отправитель с новыми таймаутами (около 25 секунд на одно уведомление при медленном Telegram);
- отправка по WebSocket — **вообще без таймаута**, поэтому зависшее соединение игрока могло держать запрос неограниченно;
- в выкупе уведомления шли **по одному на каждый лот подряд**, в пакетном одобрении выводов — по одному на каждую заявку.

## Что изменено
- `core/notify.py`: новая функция `notify_user_background()` — уведомление уходит в фон (с общим таймаутом 60 с), админ получает ответ сразу. Уведомления по-прежнему доставляются.
- `core/notify.py`: если бот уже попытался отправить сообщение и Telegram не ответил, запасной отправитель больше не ждёт тот же Telegram второй раз. Он используется только если бот недоступен.
- `core/websocket.py`: отправка одному игроку ограничена 5 секундами, зависшее соединение отключается; рассылка всем идёт параллельно.
- `server.py`: фоновые уведомления в одобрении вывода, отклонении вывода, выкупе лотов и удалении лота админом. В лог пишется время по этапам: `⏱ withdrawal …: prepare …s, TON payout …s`, `⏱ admin buyout: N lots in …s`.
- `ton_integration.py`: баланс второго кошелька (V3R2) запрашивается только если на основном (V4R2) не хватает средств — на один запрос к Toncenter меньше. Если `TONCENTER_API_KEY` не задан, в лог пишется предупреждение (без ключа Toncenter даёт около 1 запроса в секунду, и выплаты ждут из-за ошибок 429).

## Замеры (тестовый Telegram с задержкой ответа 9 с, тестовый Toncenter)
| Операция | До | После |
|---|---|---|
| Выкуп 3 лотов | 27,3 с | 0,3 с |
| Выкуп 10 лотов | ~90 с (по расчёту) | 0,8 с |
| Одобрение вывода | 9,7 с | 0,4 с |

На реальном сервере время одобрения вывода теперь определяется только ответами Toncenter (обычно 1–3 секунды). Если в логе `TON payout` стабильно больше нескольких секунд, задайте `TONCENTER_API_KEY` (бесплатный ключ выдаёт бот @tonapibot).

## Тесты
`backend/tests/test_admin_speed.py` — 5 тестов: зависший WebSocket не держит запрос, рассылка параллельна, фоновое уведомление не блокирует вызывающий код и не роняет его ошибками, Telegram не ждётся дважды.

Чтобы понять, работают ли задания и новый онбординг: вернулся ли игрок на следующий день, через неделю, через месяц, и на каком шаге новички отваливаются. Это же даёт цифры для A/B из онбординга (группы «задания» и «обучение»).

## Что добавлено
**`backend/analytics.py`** — модуль и админский API:
- `user_active_days` — по одной маленькой записи на (игрок, день по МСК), когда игрок был активен. Пишется при входе и при любом игровом действии (смена, сбор, продажа, покупка, ремонт, апгрейд, лот). Повторно за день не пишется.
- `analytics_events` — события воронки: `register`, `first_business`, `first_shift`, `first_sale`, `onboarding_completed`. Пишутся один раз на игрока. Ничего чувствительного: только id, имя события и грубые признаки (группа онбординга, канал).
- Когортный ретеншен D1/D7/D30 по дню регистрации; воронка новичка; DAU по дням. Границы суток — по Москве.

**Эндпоинты** (только для админа):
| Путь | Что отдаёт |
|---|---|
| `GET /api/admin/analytics/retention?days=30&group=all` | возврат D1/D7/D30 по когортам и итогом |
| `GET /api/admin/analytics/funnel?days=30&group=all` | воронка: регистрация → бизнес → смена → продажа → прошёл путь |
| `GET /api/admin/analytics/active?days=14` | DAU по дням |
| `GET /api/admin/analytics/overview?days=30&group=all` | всё сразу |

`group` принимает `all`, `quests`, `tutorial` — для сравнения двух вариантов онбординга.

**Фронтенд:** новая вкладка «Удержание» в админке (`components/admin/RetentionPanel.jsx`): карточки D1/D7/D30, воронка, график DAU, таблица когорт, переключатель группы и периода (7/30/90 дней).

**Хуки записи:** регистрация — в `auth_handler.py` (email) и `routes/auth_wallet.py` (кошелёк); активные дни — при входе и из движка заданий на каждом игровом событии; вехи воронки — из `quests.py`.

## Важно про исторические данные
Ретеншен и DAU считаются от момента, когда этот код появился в проде: до него записей активных дней не было. Поэтому первые дни после выкладки цифры будут неполными, это нормально — данные копятся со дня запуска. Регистрация и «есть бизнес» считаются и для старых игроков (по полю `created_at` и наличию бизнеса).

# Безопасность: поиск по пустому кошельку и секреты

## 1. Поиск пользователя по пустому кошельку (денежный баг)
**Проблема.** Примерно в 45 местах пользователь искался или обновлялся по `{"wallet_address": current_user.wallet_address}`. У игроков, вошедших по email, `wallet_address` пуст (`None`), а запрос `{"wallet_address": None}` в MongoDB находит **любого** игрока без кошелька. Из-за этого:
- доход с бизнеса и ресурсы могли зачислиться **другому** игроку;
- аренда склада, покупка участка с перепродажи, постройка и снос могли списать деньги не с того;
- запрос на вывод и список контрактов могли относиться к чужому аккаунту.

Проверено воспроизведением: запрос вывода для обычного игрока возвращал запись администратора.

**Как исправлено.** Для текущего игрока поиск и списание теперь идут по стабильному `id` (он есть всегда). Там, где нужен перебор идентификаторов, добавлен помощник `core/helpers.py::nz_or()` — он выбрасывает из `$or` условия с пустым значением, а если не осталось ни одного, запрос не находит никого (вместо «найти всех»). Значения, которые записываются как `owner`/`renter_id`/`seller_id`, теперь берутся через `owner_key()` — он никогда не вернёт `None` (кошелёк, иначе id).

Итог по `server.py` и модулям `routes/*`: ~60 мест переведено на поиск по id, 14 записей владельца — на `owner_key`, несколько `$or` — на `nz_or`. Защита в `core/balance.py` (из прошлого этапа) остаётся как последний рубеж.

## 2. Секреты
- **`ADMIN_SECRET`** больше не имеет публичного значения по умолчанию `admin-secret-key-2025` (убрано из `core/config.py` и `server.py`).
- **`backend/security_checks.py`** — проверка при старте: в production (`ENV`/`ENVIRONMENT`/`APP_ENV` = `production`/`prod`) сервер **не запустится**, если `ADMIN_SECRET` или JWT-секрет пусты, слишком короткие или совпадают с известными дефолтами. Вне production — только предупреждение, локальная разработка не ломается.
- **Пароли убраны из репозитория.** `create_test_users.py`, `seed_users.py`, `routes/auth_wallet.py` теперь читают пароли из `SEED_ADMIN_PASSWORD` / `SEED_USER_PASSWORD` (без публичных дефолтов; `create_test_users.py` падает с подсказкой, если они не заданы). В `memory/PRD.md` пароли скрыты.

**Важно:** пароли уже были в истории git. Эти правки убирают их из текущего кода, но в старых коммитах они остаются — **смените пароль администратора на боевом сервере** и задайте новый `ADMIN_SECRET` (`openssl rand -hex 32`).

## Настройка (добавить в прод-окружение)
```
ENV=production
ADMIN_SECRET=<openssl rand -hex 32>
# пароли для сид-скриптов (не коммитить):
SEED_ADMIN_PASSWORD=<...>
SEED_USER_PASSWORD=<...>
```

## Тесты

# Серия входов (щит) и бонус возвращения

## Бонус возвращения
Игрок, которого не было несколько дней, при возвращении получает одноразовый подарок — чтобы не вернуться на пустой склад и не уйти снова.
- **3+ дня отсутствия:** бонусные $CITY + защита склада от полуночной потери на 24 часа.
- **14+ дней:** больше $CITY + защита на 48 часов + 1 щит серии.

«Отсутствие» считается по `user_active_days` (из аналитики): последний активный день до сегодняшнего. Подарок выдаётся один раз за возвращение (атомарно, повторно получить нельзя), награда идёт на бонусный баланс. Все суммы настраиваются в админке.

## Щит серии
Щит сохраняет серию ежедневного входа при пропуске одного дня (хранится максимум 2). Где берётся:
- выполнить все 3 недельные цели (раз в неделю);
- большой бонус возвращения.

Ежедневная награда (`/daily`, `/daily/claim`) теперь сама «прощает» пропущенные дни, если щитов хватает, и тратит их. Заодно получение награды стало **атомарным** — двойной клик больше не начислит её дважды.

## Защита склада
Полуночная потеря 10% склада (`background_tasks.py::midnight_decay`) пропускает игроков с активной защитой из бонуса возвращения.

## Новое
- **`backend/comeback.py`** — логика бонуса и щитов; API: `GET /api/comeback`, `POST /api/comeback/claim`, `GET/PUT /api/admin/comeback/config`.
- Поля пользователя: `streak_shields`, `comeback_claimed_for`, `decay_protected_until`, `shield_week`.
- **`frontend/src/components/ComebackBanner.jsx`** — баннер подарка и индикатор щитов над ежедневной наградой (9 языков).

## Тесты
`backend/tests/test_comeback.py` — 8 тестов: тиры 3/14 дней, выдача один раз за возвращение, параллельные запросы платят один раз, щит за большой бонус, лимит 2 щита, настройка из конфига, защита склада.

# Полный склад останавливает все бизнесы

## Как должно работать
- Склад игрока полностью заполнен → **все** его бизнесы простаивают (статус «простаивает», причина «склад полон»): не производят и не тратят сырьё.
- Появилось место, смена бизнеса идёт и сырьё есть → бизнес снова **активен** и работает.
- Смена не запущена → простаивает («смена окончена»), даже если место есть.

## Почему раньше бизнесы работали на полном складе
Проверка заполненности в экономическом тике была, но считала склад иначе, чем интерфейс:
1. **Не учитывались ресурсы, выставленные на рынок.** Интерфейс («Мой бизнес») и покупка на рынке считают лоты занятым местом, а тик — нет. Игрок видел «склад полон», а тик считал, что место есть, и продолжал производство.
2. **Склад одного игрока дробился.** Тик группировал бизнесы по строке владельца. Если часть бизнесов записана на `id`, а часть на кошелёк или e-mail, вместимость и занятость считались по кускам.
3. **Статус на экране доверял тику** и мог показывать «активен», пока тик ещё не отработал.

## Что исправлено
- `background_tasks.py::economic_tick`: занятость = ресурсы на складе **+ ресурсы в активных лотах** (как в интерфейсе); бизнесы группируются по одному ключу игрока (`id`), вместимость — по всем его бизнесам; карта игроков дополнительно индексируется по e-mail.
- `server.py` (`/my/businesses`): статус сразу учитывает реальную заполненность склада — при полном складе «простаивает», как только место освободилось (и смена идёт, и сырьё есть) — «активен», не дожидаясь следующего тика. Производство возобновляется на ближайшем тике (раз в минуту).

## Проверено
Настоящий тик на локальной базе, 5 сценариев: место есть → работает; склад полон из-за лота → остановлен; лот снят → возобновился; склад полон ресурсами → остановлен; смена окончена → простаивает. Старый код на сценарии «полон из-за лота» продолжал производить (10 → 14,58 энергии), новый — нет.

## Тесты
`backend/tests/test_warehouse_full.py` — 6 тестов на настоящем `economic_tick`. На старом коде падают 3 из них.

# Умные уведомления (в игре + Telegram)

## Что приходит
| Уведомление | Когда |
|---|---|
| 📦 Склад полон — бизнесы остановились | склад заполнен на 100%, а смена хотя бы у одного бизнеса идёт |
| 📦 Склад почти полон | склад заполнен на 90%+ (бизнесы скоро встанут) |
| 🔧 Прочность N% | бизнес опустился ниже 20% |
| ⛔ Бизнес остановился | прочность бизнеса упала до 0% |
| 📈 Цена на ресурс выросла | рыночная цена ресурса, который игрок производит или хранит (20+ ед.), выросла на 15%+ за сутки |

**Про цены:** базовые цены ресурсов в проекте зафиксированы (тик выставляет их из таблицы, динамика отключена). Поэтому «цена выросла» считается по **рынку игроков** — медианной цене активных лотов (минимум 3 лота), раз в час сравнивается со снимком суточной давности.

## Правила доставки
- **В игре** (колокольчик + мгновенно по WebSocket) — приходят **всегда**, без лимита. В уведомлении есть кнопка «На рынок» или «К бизнесам».
- **Telegram** — максимум **1 или 2 в день** (выбор игрока, по умолчанию 2). Одно сообщение в день всегда остаётся за важными (склад полон, бизнес остановился) — подсказка о цене не может занять последний слот.
- **Тихие часы** (по умолчанию 23:00–08:00 по часовому поясу игрока, он берётся из браузера) — Telegram не отправляется, сообщение ждёт в очереди и уходит после окончания тихих часов, **только если ещё актуально** (например, склад всё ещё полон).
- Каждый тип можно выключить.
- **Без повторов:** склад — по состоянию «норма / почти полон / полон» с гистерезисом (повторно только после того, как склад опустился ниже 80%); прочность — один раз на каждый износ (снова — после ремонта до 50%+); цена — один раз в сутки на ресурс. Всё хранится в базе, поэтому перезапуск сервера не вызывает повторов.

## Переводы — через LibreTranslate
- **Тексты уведомлений:** английский и русский написаны вручную, остальные 7 языков переводятся с английского через LibreTranslate (переменные вроде `{count}` защищены). Переводы кешируются в `smart_notif_i18n` и при старте сервера прогреваются в фоне. Если LibreTranslate недоступен или испортил переменную — игрок получает английский, а не сломанный текст.
- **Подписи интерфейса** (настройки, кнопки) добавлены в общий словарь `translationsExtra` на en/ru; остальные языки заполняет `npm run i18n:autofill`.

## Заменено
Старые уведомления о прочности в тике (только Telegram, 4 порога 50/20/10/0% на каждый бизнес, без лимита, состояние в памяти процесса) заменены на умные: 20% и 0%, в игре и в Telegram, с лимитом и тихими часами.

## Новое

# Исправления по заданиям

## 1. Смена останавливалась после задания «Улучшите бизнес»
**Причина.** Бесплатно застолблённый бизнес «уровня 0» работает сам, без смены (у него нет кнопки смены). При улучшении до уровня 1 флаг «работает сам» снимался, а смену никто не запускал — бизнес вставал, и появлялась активная кнопка «Запустить смену». Задание «Улучшите бизнес» как раз подталкивает игрока к этому улучшению.

**Исправление** (`routes/business_mgmt.py`): при улучшении с 0 до 1 сразу запускается смена (8 часов), бизнес продолжает работать без перерыва. Автозапущенная смена засчитывается в задание «Запустите смену» — раньше игроки с бизнесом уровня 0 не могли выполнить этот шаг до улучшения.

## 2. «Путь новичка»: выполненные шаги скрываются
Полученные шаги больше не показываются. Когда последний шаг выполнен, раздел исчезает. Исключение — выбор бесплатного ресурса тира 3 в конце пути: он остаётся, пока игрок его не выберет, иначе награду было бы негде забрать.

## 3. Ежедневная награда без «купить 30 / продать 95»
Условие торговли убрано и на сервере, и в интерфейсе. Ежедневную награду теперь открывает выполнение любой одной цели из блока «Сегодня». Текст подсказки — в общем словаре (en/ru; остальные языки через `npm run i18n:autofill`), сообщение сервера на других языках — через LibreTranslate.

## 4. Значок на кнопке «Задания» в «Моих бизнесах»
На кнопке «Задания» появился красный бейдж с количеством наград, которые можно забрать (тот же счётчик, что красная точка в меню).

Только цвета проекта: `#030304`, `#00F0FF`, `#7000FF`, `#0098EA`.
- **Лёгкий для устройств:** сетка и свечение — статичные CSS-градиенты (рисуются один раз); двигаются только 8 импульсов (на телефоне 4), и анимируется только `transform`/`opacity` — это делает видеокарта, без перерисовки страницы. Анимация ставится на паузу, когда вкладка скрыта, и выключается при системной настройке «уменьшить движение», режиме экономии трафика и на слабых устройствах (≤ 2 ядер / ≤ 1 ГБ памяти) — там фон остаётся статичным.
- **Как подключён:** слой фиксирован позади приложения (`z-index: -1`, не перехватывает клики). Корневые блоки страниц (`h-screen`/`min-h-screen` с `bg-void`) сделаны прозрачными, чтобы фон был виден; модальные окна и карточки с `bg-void` остаются непрозрачными.

# Рефакторинг: общие правила вместо копий

**Зачем.** Большинство багов, которые мы чинили, были одного происхождения: одно правило игры скопировано в несколько мест, и копии разошлись. Склад считался по-разному в пяти местах (отсюда «бизнесы работают на полном складе»), правило смены жило в трёх местах (отсюда кнопка смены у уровня 0), определение владельца — в двух версиях, одна из которых осталась с опасным поиском по пустому кошельку. Весь `server.py` я не переписывал — вынес именно эти правила в общие модули.

## 1. Склад игрока — `backend/core/warehouse.py`
Одно правило: занято = ресурсы (с весами тиров) + ресурсы в активных лотах; вместимость = склады всех бизнесов игрока с баффом склада, минимум 50.

Переведены на него все пять мест: экран «Мой бизнес», покупка на рынке и ручной сбор, выкуп админом, экономический тик, свалка.

Найденные и исправленные расхождения:
- **свалка** и **выкуп админом** не учитывали бафф склада («Глубокие закрома», +10%) — игрок с баффом не мог подобрать мусор, хотя место было;
- бизнес без вместимости: экран считал склад 50, рынок — 0, тик — «никогда не полон». Теперь везде 50 (как видел игрок).

Проверено: экран «Мой бизнес» показывает ровно те же числа, что до замены, в 4 сценариях (без бизнеса, два бизнеса, с лотами, бизнес без вместимости).

## 2. Работает ли бизнес — `backend/core/business_rules.py`
`shift_is_active`, `auto_operates` и длительность смены (8 ч) — в одном месте. Тик и сервер используют одну функцию. Фронтенд больше не повторяет правило: кнопка смены берёт готовый признак `auto_operates` из `/my/businesses`.

## 3. Кто владелец — `backend/core/helpers.py`
- Две разные версии `get_user_identifiers` сведены в одну: поиск по стабильному `id` (без опасного поиска по пустому кошельку), возвращает `primary_id`, учитывает и `username`. В `server.py` осталась тонкая обёртка.
- Копии `get_businesses_query` и `is_owner` из `server.py` удалены — используется версия из `core/helpers.py`.
- Задания и аналитика искали бизнес только по полю `owner`. Теперь — по общему правилу (`owner` или `owner_wallet`, по id, кошельку, e-mail или username). Раньше игрок с бизнесом, записанным на username, не получал задание «Откройте бизнес».

## Тесты
`backend/tests/test_warehouse_rules.py` (8) и `backend/tests/test_shared_rules.py` (5): правило склада, бафф, лоты, минимум 50, согласованность свалки; правило смены и что тик и сервер используют одну функцию; владелец не путается с чужим аккаунтом; бизнес находится по `owner_wallet` и `username`.

# Городской рынок (системный маркет-мейкер)

**Зачем.** При малом онлайне новичок не может ни купить сырьё, ни продать продукцию, а шаг «Продайте ресурс» в «Пути новичка» зависает. Городской рынок — страховочная сетка, а не конкурент игрокам: он **покупает дешевле и продаёт дороже** рынка игроков, поэтому игрокам всегда выгоднее торговать друг с другом. Для игроков он подписан честно: «Городской рынок» (в лотах и в уведомлении продавцу).

## Как работает (каждые 5 минут, `backend/market_maker.py`)
- **Покупка у игроков.** Лот игрока, который висит дольше 30 минут и стоит не дороже 70% базовой цены, выкупается. Для продавца это обычная продажа: налоги, кредиты, рефералы, «налоговая гавань» и казна считаются той же функцией, что и выкуп админом (`server._admin_buyout_apply_sale`, расширена параметрами).
- **Гарантия новичку.** Первая в жизни продажа игрока — до 10 единиц по цене не выше базовой — выкупается через 2 минуты. Засчитывается в шаг «Продайте ресурс».
- **Куда деньги продавцу** (ваше правило): на **реальный** баланс, если у продавца есть бизнес уровня 1+; иначе (только уровень 0 или нет бизнесов) — на **бонусный** (`zero_business.city_market_payout_is_real`).
- **Продажа игрокам.** По одному лоту на ресурс по 130% базовой цены, только из купленного запаса — ресурсы из воздуха не создаются. Лоты пополняются и снимаются по запасу.

## Защита
Аварийный выключатель (по умолчанию **выключен**); дневной бюджет реальных выплат (по умолчанию **0** — задаётся в админке); отдельный лимит бонусных выплат; лимиты на игрока в день по TON и единицам — **аккаунты с одного устройства считаются одним игроком**; лимит запаса на ресурс; максимальная доля одного игрока в покупках дня; атомарный резерв лота (игрок и рынок не могут купить одни и те же единицы); журнал всех сделок `mm_trades`.

## Аналитика — админка, вкладка «Городской рынок»
- Куплено/продано (TON и единицы, реальные и бонусные выплаты), результат с учётом стоимости запаса, сколько продавцов/покупателей и новичков обслужено.
- **Сегодня:** использование дневного бюджета и бонусного лимита.
- **Ликвидность** — главный показатель: медианное время продажи лота игрока за период и за предыдущий такой же период, доля лотов, проданных игрокам и рынку.
- Объём по дням, таблица по ресурсам (средние цены, запас, на сколько дней хватит), «кто больше всех продаёт рынку» (с числом аккаунтов на устройстве), последние сделки, предупреждения (выключен / бюджет 0 / бюджет исчерпан / один игрок забирает больше заданной доли).
- **Управление:** включение, бюджет, проценты покупки и продажи, задержка, лимиты, гарантия новичку, продажа из запаса, список ресурсов, кнопка «Запустить цикл».

API: `GET/PUT /api/admin/market-maker/config`, `GET /api/admin/market-maker/analytics?days=7`, `GET /api/admin/market-maker/trades`, `POST /api/admin/market-maker/run`.

## Попутно исправлено
**Покупка на рынке теряла единицы при сбое базы.** `/market/buy` сначала резервирует единицы в лоте, потом списывает деньги. Если списание падало с ошибкой базы, резерв не возвращался — лот продавца уменьшался без продажи. Теперь резерв возвращается и в этом случае (проверено вживую).

## Проверено
- Автотесты `backend/tests/test_market_maker.py` (14): выключатель, выкуп старого дешёвого лота, правило выплат (уровень 1+ → реальный, только уровень 0 → бонусный, смешанный → реальный), не трогает свежие и дорогие лоты, гарантия новичку 10 из 40 единиц и только один раз, бюджет, лимит на устройство, лимит запаса, лимит доли, продажа из запаса и учёт покупок игроков, не покупает свои и админские лоты, проверка настроек, аналитика.
- Вживую с настоящим расчётом денег: продавец с бизнесом 1 уровня получил +0,0945 TON на реальный баланс (0,105 − 10% налога), новичок с бизнесом 0 уровня — +0,0297 на бонусный; уведомление «Городской рынок купил ваш лот»; задание новичка засчиталось; рынок выставил лоты по 130%.

## Важно
- Чтобы рынок заработал: в админке включить его и задать **дневной бюджет**. Пока бюджет 0, рынок выкупает только с выплатой на бонусный баланс (новичкам), а за реальные деньги не покупает.
- **Два правила «куда деньги продавцу».** Для обычных продаж между игроками действует старое правило: на бонусный, если у продавца есть хоть один бизнес уровня 0. Для Городского рынка — ваше: на реальный, если есть хоть один уровня 1+. Они расходятся только у тех, у кого есть и 0, и 1+.

# Городской рынок: правила по типу продавца и выбор ресурсов

## Почему понадобилось
Новичок (у кого есть бизнес уровня 0) **не может задать цену** — его лоты выставляются по системной цене (≈ базовой, округлённой). Игрок с бизнесом 1+ пишет цену сам. Прежнее правило «выкупать лоты не дороже 70% базовой» поэтому никогда не срабатывало для новичка после его первой продажи — в пустом рынке он оставался с непроданным товаром.

## Правила теперь
| Продавец | Цена | Когда выкупает Городской рынок | Куда деньги |
|---|---|---|---|
| Только бизнесы уровня 0 (новичок) | системная, автоматически | первая продажа — через 2 мин (до 10 ед.); все следующие лоты — через 30 мин **по его системной цене** | бонусный |
| С бизнесом уровня 1+ | пишет сам | через 30 мин, если цена не выше 70% базовой | реальный, из дневного бюджета |
| И уровень 0, и 1+ | системная (принудительно) | не выкупает (кроме первой продажи) | — |

Смешанного продавца рынок не выкупает намеренно: его цена принудительно системная, а платить пришлось бы реальными деньгами — держать бизнес уровня 0 стало бы способом продавать городу за 100% вместо 70%.

Системная цена новичка теперь живёт в одном месте — `backend/core/pricing.py` (раньше её знал только `server.py`). Городской рынок сравнивает лот новичка именно с ней, а не с таблицей, поэтому правило не сломается, если админ поменяет цены.

## Выбор ресурсов в админке
Во вкладке «Городской рынок» → «Настройки» — таблица **всех 21 ресурса** (тиры 1–3) с базовой и системной ценой и двумя переключателями: **«Выкупать»** и **«Продавать»**. Кнопки «Выкупать все тир 1» / «Продавать все тир 1» для быстрого выбора. Убранный из «Продавать» ресурс снимается с рынка на ближайшем цикле. Старая общая настройка `resources` автоматически переносится в оба списка.

Настройки: новые `buy_resources`, `sell_resources`, `auto_price_buy` (вкл/выкл выкуп лотов новичков по системной цене), `auto_price_delay_min`. API каталога: `GET /api/admin/market-maker/catalog`. В аналитике сделки разделены по причине: первая продажа, лот новичка по системной цене, дешёвый лот.

## Проверено
- Автотесты: 9 новых (всего по рынку 23): повторный лот новичка выкупается целиком по системной цене на бонусный и ждёт 30 мин; смешанный продавец и игрок 1+ не выкупаются по полной цене; гарантия новичку следует системной цене, а не таблице; списки «выкупать»/«продавать» работают; ресурсы любого тира можно включить; перенос старой настройки.
- Вживую: лот новичка (40 ед.) выкуплен на бонусный, смешанный — не выкуплен, ресурс вне списка — не выкуплен, лот рынка снят после удаления ресурса из «Продавать»; переключатель в админке сохраняет список. Скриншот: `docs/screenshots/city_market_resources.png`.

# Пакет доработок: Городской рынок, бонус возвращения, кнопка заданий, аренда, лиги

## 1. Удалён выкуп через 24 часа
Старая задача (каждые 10 минут выкупала непроданные лоты новичков старше суток, без налога, лимитов и журнала) удалена вместе с функцией и уведомлением. Лоты новичков выкупает только Городской рынок — через 30 минут.

## 2. Городской рынок — управление из админки
- **Два выключателя:** «Выкуп у новичков» (бизнес уровня 0, выплата бонусными; по умолчанию **включён**) и «Выкуп за реальные деньги» (бизнес 1+, нужен дневной бюджет; по умолчанию выключен). Третий — «Продажа из запаса».
- **Лимиты бонусных выплат** (это бонусные $CITY, которые город платит новичкам за выкупленные лоты): общий на всех новичков в день и **новый лимит на одного новичка** в день (аккаунты с одного устройства — один новичок). По умолчанию 20 000 и 500 $CITY.
- **Цены от статичной базовой цены ресурса:** выкуп = базовая − X%, продажа = базовая + Y% (проценты задаёт админ). Для любого ресурса можно вписать свою цену выкупа и/или продажи; пустое поле — автоматическая. Цена выкупа всегда должна быть ниже цены продажи (иначе через город можно гонять деньги по кругу) — сервер это проверяет.
- **Всё выкупленное выставляется на продажу целиком** по цене продажи (раньше лот был ограничен 50 единицами).
- **Сколько выкуплено и продано городом** — за сегодня и за период (в TON и единицах).
- Таблица ресурсов: базовая цена (статичная), цена выкупа, цена продажи, «Выкупать», «Продавать».

## 3. Бонус возвращения — вкладка в админке
Сроки и награды малого и большого подарка (дни отсутствия, бонусные $CITY, часы защиты склада, щиты серии) и статистика: сколько подарков выдано, сколько игроков вернулось, сколько выплачено, у скольких сейчас защищён склад и есть щиты.

## 4. Кнопка «Задания» в «Моих бизнесах»

# Выкуп бизнеса новичка; уведомление «смена закончилась»

## Бизнес новичка снова можно выкупить
По вашему решению включено обратно автоматическое выставление бизнеса уровня 0 на продажу (было отключено в версии 2.3 — в коде был комментарий, что тогда владелец не хотел автопродажи; это решение отменено).
- При получении бизнеса уровня 0 (оба места: покупка клетки и постройка) он сразу выставляется на продажу за **1,2 × цены карты** (`routes/ton_island.py::_list_zero_business`, использует существующий `zero_business.create_zero_listing`).
- Другой игрок (без бизнеса уровня 0) может выкупить его с карты: платит реальные TON и получает бизнес уровнем 1; новичок теряет бизнес и получает уведомление (это уже было в коде покупки).
- Пока новичок не улучшил бизнес до 1 уровня; после улучшения лот снимается (это тоже уже было в коде).
- **Предупреждение при получении бизнеса** дополнено: «пока вы не улучшите его до 1 уровня, его может выкупить другой игрок, а когда аренда закончится — его заберут».
- Сбой выставления никогда не ломает само получение бизнеса.

## Уведомление «смена закончилась» (в игре + Telegram)
- Новый тип умных уведомлений `shift_ended`: «⏰ Смена закончилась: {бизнесы}. Зайдите в игру и запустите новую смену…» с кнопкой «К бизнесам».
- Определяется в экономическом тике: если смена у бизнеса (включая уровень 0) закончилась, игрок получает **одно** сообщение по всем таким бизнесам сразу. Повторов нет (поле `shift_end_notified` у бизнеса). Смены, закончившиеся больше 2 часов назад (например, при первой выкладке), не присылаются.
- **Не тратит дневной лимит Telegram** (смена кончается до 3 раз в сутки — иначе вытесняла бы важные уведомления). Тихие часы соблюдаются: ночью сообщение ждёт до утра и уходит, только если смена так и не запущена.
- Игрок может выключить его в «Настройки → Умные уведомления → Смена закончилась».
- Тексты: en/ru вручную, остальные языки через LibreTranslate.

## Тесты
`test_zero_listing.py` (2), `test_smart_notify.py` +4 (без дневного лимита, выключается, ночью отбрасывается если смену перезапустили, на настоящем тике — одно сообщение на игрока и без повтора), обновлён тест в `test_v23_blocked_and_welcome_bonus.py`. Всего 122.

# Надёжность платежей: две найденные и исправленные ошибки

## 1. Терялись пополнения (критично)
`payment_monitor.py` пропускал транзакцию, если её время в блокчейне раньше момента обработки предыдущего пополнения того же игрока (`last_deposit_processed_at`). Toncenter отдаёт транзакции от новых к старым, поэтому при **двух пополнениях игрока за один опрос** (раз в 10 секунд) старшее отбрасывалось, курсор уходил дальше — и деньги **не зачислялись никогда**.

Воспроизведено: игрок отправил 3,0 TON двумя переводами — зачислено 2,0, вторая транзакция даже не записана.

**Исправление:** проверка по времени удалена. Защита от повторного зачисления — уникальный индекс `deposits.tx_hash`: запись о пополнении создаётся **до** зачисления, поэтому ни второй обработчик, ни повторный опрос не зачислят одну транзакцию дважды. Если процесс упадёт между записью и зачислением, пополнение останется в статусе `crediting` — оно не зачислится дважды, а будет видно для ручной проверки.

**Важно при выкладке:** если в базе уже есть дубли `tx_hash` в `deposits`, уникальный индекс не создастся (в логе будет ошибка `deposits.tx_hash unique index NOT created`) — тогда дубли нужно убрать.

## 2. Двойная оплата при сбое после выплаты
При одобрении вывода, если TON уже ушёл с кошелька, а следующая запись в базу упала, общий обработчик ошибок **возвращал деньги на баланс** и помечал заявку «не выполнена» — игрок получал деньги дважды.

Воспроизведено на старом коде: возврат 0,51 TON после отправленной выплаты, хеш транзакции потерян.

**Исправление:** после успешной отправки возврат невозможен; заявка получает статус `needs_review` с сохранённым хешем, админ получает сообщение «Выплата отправлена, но запись не сохранилась — повторно не одобряйте».

## Тесты
`backend/tests/test_payment_deposits.py` — два пополнения за опрос зачисляются оба; одна транзакция не зачисляется дважды (последовательно и параллельно). Защита выплаты проверена вызовом настоящей функции одобрения с подменённой отправкой и сбоем базы.

# Сверка платежей и неясный исход выплаты

## Неясный исход выплаты
Если запрос отправки TON (`sendBoc`) к Toncenter обрывался по таймауту или сбою шлюза, ошибка уходила в обработчик одобрения, и тот **возвращал деньги игроку** — хотя перевод мог уже уйти в сеть.
- `ton_integration.py`: при сетевом сбое то же подписанное сообщение отправляется повторно (безопасно: из‑за `seqno` сеть проведёт его не больше одного раза). Если ответа так и нет или сеть сообщает, что `seqno` уже использован после потерянного ответа, — выбрасывается `PayoutAmbiguous` с хешем сообщения.
- Одобрение вывода на `PayoutAmbiguous`: статус `needs_review`, хеш сохраняется, **без возврата**.
- Проверено с настоящей подписанной транзакцией и тестовым Toncenter, отвечающим ошибкой шлюза: 3 повтора, затем «требует проверки», баланс игрока не изменился.

## Вкладка «Сверка» в админке (`backend/reconciliation.py`)
- **Покрытие:** баланс кошельков проекта в блокчейне − (реальные балансы игроков + выводы в очереди). Бонусные балансы показываются отдельно (не выводятся).
- **Что требует решения:** выводы `needs_review`, выводы, зависшие в обработке > 15 мин, пополнения, зачисление которых не завершилось. У каждого — ссылка на транзакцию (tonviewer) и действия: «Выплата ушла — подтвердить» / «Не ушла — вернуть на баланс», «Зачислить» / «Отклонить». Каждое действие — атомарный переход статуса, двойное нажатие не заплатит дважды; всё пишется в журнал админа.
- **Кошельки проекта:** адреса приёма платежей и кошельки распределения подтягиваются автоматически, можно добавить свои; порог предупреждения по покрытию.
- **Ежедневная проверка:** раз в сутки отчёт сохраняется в историю, при проблемах админам приходит уведомление (в игре и в Telegram). Кнопка «Проверить и уведомить» — запустить сейчас.

## Тесты
`backend/tests/test_reconciliation.py` — покрытие и предупреждение о нехватке TON, список застрявших операций, зачисление и подтверждение/возврат ровно один раз (в том числе при параллельных нажатиях), предупреждение без кошельков.

# City Pass и «Усилители»

## City Pass (`backend/city_pass.py`, страница `/city-pass`)
- **Сезон** 30 дней, 30 уровней. **Последний уровень = 80% от максимально возможного XP за сезон:** XP за уровень = 0,8 × дней × макс. XP в день / уровней (по умолчанию 0,8 × 30 × 200 / 30 = 160). Пересчитывается автоматически при изменении настроек.
- **XP** за те же действия, что задания и лиги (цели дня/недели, смены, ремонт, продажи игрокам, день серии, топ-5 недели в лиге), с лимитами на действие и на день. Продажи Городскому рынку и между связанными аккаунтами не считаются.
- **Награды — только предметы, без бонусного баланса:** бесплатная награда **на каждом уровне**, премиум — **дополнительные награды на уровнях 1, 5, 10, 15, 20, 25, 30**. На 30-м уровне — **автозапуск смен на 3 дня**.
- Награду можно получить, **только когда уровень пройден и нажата кнопка «Забрать»** (есть «Забрать всё»); премиум-награды — только с купленным премиумом. Каждое получение атомарно — дважды не выдаётся.
- **Премиум** — 3 TON, **только с реального баланса** (бонусный не считается); открывает и уже пройденные уровни.
- После конца сезона награды можно забрать ещё 3 дня (настраивается).
- Карточка City Pass в «Моих бизнесах» теперь активна: уровень, полоса XP, число готовых наград, спокойная пульсация, если есть что забрать. Уведомление в игре при новом уровне.
- **Админка → City Pass:** сезон (название, дни, уровни, макс. XP в день, доля 80%, дни на получение, цена премиума), XP и лимиты, **редактор наград по каждому уровню** для обеих дорожек, «Начать новый сезон»; аналитика — игроки по уровням, премиум и выручка, полученные награды, возврат на 2-й неделе у игроков паса против остальных.

## «Усилители» (`backend/boosters.py`, «Ресурсы» → «Усилители»)
Непродаваемые предметы в стиле награды тира 3 за обучение: не продаются, не занимают склад, включаются игроком.
- **Автозапуск смен на N часов** — закончившиеся смены всех бизнесов игрока сами запускаются заново (встроено в экономический тик; уведомление «смена закончилась» при этом не приходит).
- **Защита склада на N часов** — нет полуночной потери 10%.
- **Ремонт всех бизнесов** — сразу до 100%.
- **Щит серии** и **предмет тира 3** (`<ресурс>_tutorial`, включается как бафф через существующий механизм, максимум 2 баффа тира 3).
- Время одинаковых усилителей складывается. Каждый предмет тратится ровно один раз.

# City Pass: ступени XP, цена от админа; автозапуск ждёт сырьё; нагрузка на сервер

## Ступенчатая стоимость уровней
Уровни разбиты на три ступени — 1–10, 11–20, 21–30 — и каждая следующая дороже. Вес ступеней задаёт админ (по умолчанию 0,8 / 1,0 / 1,2 → **128 / 160 / 192 XP** за уровень). Сумма всех уровней по-прежнему ровно **80% максимума сезона** (4800 из 6000 XP); меняется только распределение. В админке — поля весов с предпросмотром XP по ступеням, на странице паса под номером уровня видна его стоимость.

## Цена премиума — только от админа
По умолчанию цены нет, и премиум **не продаётся** (игрок видит «Скоро»). Админ вписывает цену в TON (оплата с реального баланса); 0 и отрицательные значения не принимаются.

## Автозапуск смен, когда работать нельзя
Раньше автозапуск запускал смену даже без сырья или при полном складе — бизнес простаивал, а смена «сгорала» и бизнес изнашивался. Теперь при активном автозапуске:
- **нельзя работать** (нет сырья хотя бы на час, склад полон, прочность 0) — смена не запускается, а авто-смена останавливается; бизнес простаивает **без износа**, на экране причина: «нет ресурсов» / «склад полон»;
- **проблема исправлена** — на ближайшем тике (раз в минуту) смена запускается сама и бизнес работает дальше;
- смену, которую игрок запустил сам, автозапуск не трогает; уведомление «смена закончилась» при автозапуске не приходит.

## Нагрузка на сервер
- **Кеш настроек** лиг, City Pass и Городского рынка в памяти на 30 с (`core/ttl_cache.py`): раньше каждое игровое событие (смена, ремонт, продажа) читало 2–3 документа настроек из базы. Сохранение в админке сбрасывает кеш сразу; кеш привязан к своей базе и не может вернуть чужие данные.
- **29 индексов** для горячих запросов — тик, рынок, Городской рынок, сверка, уведомления, City Pass (`core/db_indexes.py`), создаются в фоне при старте; каждый отдельно, ошибка одного не мешает остальным.
- **Сверка** считает суммы балансов агрегацией в MongoDB, а не перебором всех игроков в Python.
- **Счётчик заданий** (опрос раз в минуту с каждого клиента) кеширует список активных заданий на 60 с.
- **Городской рынок** запоминает продавца, правило выплаты и «первую продажу» внутри цикла — один игрок с многими лотами больше не порождает повторные запросы.

Переход теперь запускается и при старте сервера, и **при первом запросе карты** (`/api/island`), с блокировкой в базе, чтобы два процесса не делали это одновременно.
2. **История операций:** типы `quest_reward`, `city_pass_premium` и операции аренды переведены на 9 языков; оплата премиума и заморозка под аренду показываются со знаком «−», поступления — «+»; служебные движения аренды (списание из замороженного, комиссия) игроку не показываются.
3. **Скины:** один раздел «Данные → 🎨 Скины». «Стандарт» = здания карты (базовый скин каждого игрока; замена, размеры, предпросмотр). Другие группы — картинка на бизнес и стадию (ур. 0–3 / 4–6 / 7–10), обрабатываются как здания (фон, фундамент) и встают на участок точно (`/api/admin/skins/upload`, данные посадки в индексе скинов). Старые картинки группы `standard` перенесены в группу «Классика (старый стандарт)» — ничего не удалено.

# Без дневного лимита XP, детали покупки ресурсов, уведомления на 9 языках, загрузка → «Мои бизнесы»

1. **City Pass:** дневного лимита XP больше нет (и строки «Сегодня X / 200 XP»). Параметр `daily_xp_cap` остался только для расчёта стоимости уровней (в админке подписан «Расчётный XP в день — не лимит»). Ограничения отдельных действий (например, 3 смены в сутки) сохранены против накрутки.
2. **История операций → детали покупки/продажи ресурса:** «Количество» (а не «Сумма») для числа единиц, «Сумма ($CITY)» и «Цена за 1 ед.»; у продавца — сумма и цена за единицу с учётом налога. 9 языков.

# Мелкие хвосты: XP заданий, ссылки на владельца, CSP, иконки баффов

- **XP заданий = как на карточке:** дневные, недельные и задания новичка дают в City Pass ровно столько XP, сколько написано на задании (раньше дневные/недельные давали фиксированные 30/100). Устаревшие строки «Цель дня/недели» убраны из таблиц XP (страница и админка); на странице — «Задания — XP как на карточке».
- **Ссылки на владельца → ID:** `scripts/normalize_owner_ids.py` (dry-run / `--apply`) переводит владельцев/продавцов/покупателей, записанных кошельком или почтой, на ID игрока (бизнесы, участки, лоты, рынок, контракты); сервер делает это один раз при старте, повтор безопасен.

Встроенные скрипты разрешены по SHA-256, считается при сборке (`frontend/scripts/csp.js`, `INLINE_RUNTIME_CHUNK=false`); разрешены Telegram, вход Google, Cloudflare Turnstile. Проверено: приложение и карта работают, нарушений нет.
- **Иконки баффов** в «Активных бафах» — как на сервере (🔮 Разгон системы и т.д.), если у сохранённого баффа иконки нет.

# Первая мини-игра как акция: «Неделя Сортировщика»

- **Игра «Сортировщик»** (бизнес «Свалка»): 60 предметов на ленте — металл, батареи, микросхемы, стекло — в свои контейнеры, опасный ☢ пропустить. Окно решения 1,6 → 0,6 с, опасных к концу больше, серия без ошибок ×2/×3. Около минуты.
- **Честный счёт:** «зерно» партии выдаёт сервер; телефон присылает только нажатия, сервер сам пересчитывает очки по тем же правилам (`frontend/src/minigames/sorterCore.js` = `backend/minigames_sorter.py`, совпадение проверяется тестом). Нажатия быстрее 0,15 с не засчитываются; партия, «длящаяся» дольше реального времени, отклоняется; один результат на сессию; нажатия сохраняются для разбора спорных случаев.
- **Акция:** баннер на «Моих бизнесах», страница `/minigames/sorter` (правила, попытки, рекорд, место, рейтинг), 3 попытки в сутки (МСК), XP City Pass за звёзды (10 / 20 / 35), призы топу на бонусный баланс по окончании (1 — 5 000, 2–3 — 2 500, 4–10 — 1 000 $CITY), уведомление победителям.
- **Админка → «Мини-игры»:** включение, даты, попытки, XP за звёзды, призы по местам, ID акции (новый ID = новый рейтинг), статистика (сыграно, игроков, отклонено, звёзды), топ-50.
- 9 языков у всего, что видит игрок. Акция по умолчанию выключена — включается в админке.
